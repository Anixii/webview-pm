# Происхождение знаний и обновления

Первичный снимок: **30 сентября 2026**, из базы `docs/webview-app-builder`
canonical React-шаблона и применимых подтверждённых правил его владельца.
Этот исходный каталог указан для истории; для работы установленного плагина
он не требуется. Все необходимые reference-документы включены в `references/`.

После первичной копии документация в этом пакете является самостоятельным
источником знаний плагина. Изменения в прежней базе не синхронизируются
автоматически. Подтверждённые новые правила нужно фиксировать в подходящем
документе пакета и выпускать вместе с новой версией плагина. Установка плагина
сама по себе не разрешает редактировать его установленный cache: изменения
готовятся в исходниках плагина по задаче пользователя.

## Что подтверждено и что проверять

- Native-контракт перенесён из знаний на основе
  `web_view_bridge_partner_guide.docx`, переданного владельцем 3 июля 2026,
  и последующих ответов MBANK. Файл Word не требуется для чтения включённого
  [описания Bridge](references/mbank-webview-bridge.md).
- Заявленный rollout Bridge — 3 августа 2026. Это запись полученной информации,
  а не подтверждение доступности в любой установленной версии приложения.
  Проверять реальное наличие Bridge и разрешённые события в среде проекта.
- UI, helper exports, middleware, routes и mock modes отражают canonical
  шаблон на момент снимка. Они не означают, что такие файлы уже есть в целевом
  проекте. Использовать фактический API исходников выбранного релиза.
- Backend endpoints, response schemas, permissions и бизнес-статусы задаёт
  конкретный сервис. Примеры из шаблона не становятся общими контрактами.
- `Нужно уточнить`, «по текущему пониманию» и подобные пометки сохраняют
  исходную неопределённость. Не превращать их в новые обязательные правила.

## Применимые подтверждённые правила работы

В пакет перенесены правила reuse-first, модульных визуальных blocks и новой
архитектуры domain forms: сначала искать готовое решение, выделять смысловые
blocks с одним React component в implementation-файле, держать поведение формы
в sibling feature hook. Подробности — в
[UI page building](references/ui-page-building.md) и
[Forms best practices](references/forms-best-practices.md).

В рабочем проекте нужно также читать его `AGENTS.md` и активные записи
`AGENT_FEEDBACK.md`, если эти файлы есть. Требование отдельного approval для
первичного workbench не переносится как универсальное правило каждого нового
проекта: порядок согласования определяется текущей задачей и инструкциями
целевого проекта.

## Связь с версией шаблона

Источник кода задаётся в [template-source.json](../template-source.json).
Пока `repository` или `ref` не заполнены, canonical remote-источник ещё не
настроен; не заменять его случайным репозиторием или плавающей веткой.

Перед выпуском плагина проверить соответствие reference-документов выбранному
релизу шаблона: exports, theme tokens, dependencies, route helpers, scripts и
Bridge mock behavior. При bootstrap записывается разрешённый точный commit в
`.webview-template.json`; version/ref и commit позволяют воспроизвести основу
проекта. Полная процедура — в [template-access.md](template-access.md).
