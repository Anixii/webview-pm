# WebView-процессы для PM

Статус: рабочая версия на основе саммари встречи и уточнений PM. Остался открытый термин, который полезно сверить с другими PM; он отмечен в [intake-questions.md](./intake-questions.md).

Папку `webview-pm/` можно переносить целиком: нужные PM-процесс, термины и шаблоны находятся внутри неё, а ссылки ведут только на соседние файлы этой папки.

## Для чего эта документация

Помогает PM вести WebView-проект от первичного обсуждения до размещения в тестовой и production-среде: понять, какие сведения собрать у команд, какие заявки и запросы подготовить и куда передать результаты.

PM-ориентированное объяснение WebView, Bridge, `allowedOrigins`, capabilities, callback/result URL и deeplinks находится в [технической памятке](./technical-reference.md). В ней собраны сведения, нужные PM для координации проекта, без зависимости от документации разработчиков.

Подтверждённые организационные шаги описаны ниже. Если конкретное поле, адресат или срок не указан, PM-ассистент должен уточнить его, а не придумывать.

## Базовый процесс

Оплата и push — дополнительные потоки, они нужны только соответствующим проектам. Остальные шаги обычно применяются к каждому WebView-проекту.

### 1. Передать команде контекст проекта

PM знакомится с проектом и объясняет его суть команде разработки. В рамках обсуждения уточняет необходимые серверные характеристики у backend-разработчика. Общего утверждённого шаблона характеристик сервера нет.

### 2. Запросить сервер, домен и необходимые доступы

1. PM может сам создать заявку в банковской Jira на выделение серверных ресурсов. В описании кратко указывается проект и его назначение.
2. После выделения сервера и получения IP-адреса PM создаёт заявку на домен и его привязку к этому IP.
3. Почти для всех проектов нужно открыть домен в Кыргызской Республике (КР). Точный набор сетевых доступов зависит от проекта; PM определяет, какие запросы нужны.
4. Запросы на доступ к серверу/сервису банка, доступ во внешний интернет, открытие портов и SSL-сертификат оформляются в банковской Jira через **Центр поддержки → Поддержка пользователей**. Заполнить поля ФИО, должность и тематика, выбрав вариант тематики под задачу. Для доступа к серверу/сервису банка есть тематика «Доступ к серверу/сервису банка»; для других запросов название тематики отличается.

Для этих запросов используется одна форма, а описание адаптируется под задачу. Примеры:

- **Доступ в Fudo:** «Прошу предоставить доступ в Fudo для backend-разработчика компании Mdigital — [AD-аккаунт разработчика] ([ФИО]) в рамках реализации сервиса [название сервиса] в Mbank. Необходим доступ к: [IP]».
- **Доступ во внешний интернет и к адресу:** «Прошу открыть доступ с нашего сервиса [название сервиса] ([IP]) в мир, [краткая причина — необязательно]. Прошу также дать возможность отправлять запросы на адрес [домен] ([IP]) с нашего сервера [название сервиса] ([IP])».
- **Открытие портов:** перечислить порт, назначение и тип доступа. Например: `[порт] — Nginx HTTP / Frontend API — публичный (извне)`; `[порт] — Grafana / Celery / MinIO — внутренний (банковская сеть, RDP [AD-профиль])`.
- **SSL-сертификат:** «Прошу предоставить SSL-сертификат для нового сервиса внутри Mbank: [домен] ([IP])».

Дополнительные примеры писем и описаний заявок:

- **Запрос домена:**

  > Просим предоставить домен для проекта [название сервиса].
  >
  > Домен: [домен]

- **Запрос тестового сервера и доступа для проекта «Факторинг»:**

  > Просьба выделить тестовый сервер для работы по проекту «Факторинг».
  >
  > Факторинг — это финансовый инструмент, при котором компания продаёт свою дебиторскую задолженность (неоплаченные счета/накладные от покупателей) финансовой организации (фактору) в обмен на немедленное получение денег, не дожидаясь оплаты от самого покупателя.
  >
  > Характеристики сервера:
  > - 8 GB RAM
  > - 100 GB SSD
  > - 4 CPU
  >
  > Также нужен домен на вышеуказанный сервер: test-factoring.mbank.kg
  >
  > Доступ на сервер:
  > Прошу предоставить backend-разработчику проекта «Факторинг» доступ к вышеуказанному серверу через Fudo (SSH).
  >
  > AD: [AD разработчика]
  > ФИО: [ФИО]
  > Номер телефона: [номер телефона]

В этом примере домен указан вместе с запросом сервера; отдельную заявку на домен и его привязку к IP создают после выделения сервера и получения IP-адреса (см. пункт 2 выше).

Это примеры описаний, а не строгие шаблоны. Их можно адаптировать под проект. Точные сроки и дополнительные поля для заявок на сервер/домен здесь не фиксируются.

В подтверждающие указывается начальник отдела. PM должен определить нужного руководителя; список можно найти в Confluence.

### 3. Добавить сервис в тестовую среду

Для размещения WebView в тестовой среде:

1. Создать заявку в банковской Jira.
2. Выбрать отдел «Тестирования и технической поддержки ДЦРМС».
3. Отметить Кулова Искандера и Нурканова Эрхана.
4. Указать домен. Название сервиса должно совпадать с названием в письме, по которому ДЦРМС заводит сервис.
5. Jira-заявку и письмо с данными WebView отправить вместе. В письме передать origin и список capabilities; порядок отправки в пределах этой пары не важен.
6. Передать backend-разработчику полученные хэш и метод авторизации. Хэш нужен, чтобы методы авторизации работали корректно.

Шаблон письма находится в [templates/webview-setup-email.md](./templates/webview-setup-email.md).

### 4. Настроить Bridge для окружений

PM запрашивает у frontend-команды в личном сообщении или чате проекта:

- origin страницы для нужного окружения;
- список необходимых capabilities;

Нужность callback/result URL зависит от проекта. PM уточняет необходимость и адрес у команды проекта. Если URL не используются, в письме это указывается явно. Если callback/result URL нужно добавить или настроить позднее, PM может запросить это через Telegram у ДЦРМС.

Затем сведения передаются в письме для настройки WebView. Для dev, test и prod origins направляются отдельными запросами. При добавлении сервиса в тестовую среду Jira-заявку и письмо с origin/capabilities отправляют вместе.

Короткое объяснение терминов для PM:

- **Origin страницы** — адрес WebView-сайта, для которого настраивается Bridge. Это адрес окружения сайта; он отличается от deeplink, ведущего пользователя в другой экран.
- **Capability** — разрешение на native-действие в мобильном приложении. Базового набора нет: список нужно получить от frontend по пользовательскому сценарию. Например, `deepLink.open` требует `deepLinks`, `payment.start` — `payments`, `external.open` — `externalLinks`.
- **Callback/result URL** — адрес, куда flow может вернуть пользователя или результат. Если сценарий их не использует, в письме указать «не используются».

Техподдержка настраивает capabilities и разрешённые origins; origins для окружений учитываются отдельно. Таблица событий, разрешений и ограничений URL приведена в [технической памятке](./technical-reference.md).

### 5. Запросить deeplink

Deeplink запрашивается у технической поддержки ДЦРМС через Telegram-чат. Передать:

- название сервиса;
- ссылку на страницу, куда должен вести deeplink;
- partner name, если его запросит техподдержка. Его выдают после создания сервиса; значение можно взять из письма ДЦРМС.

Для целевой страницы подходит обычная ссылка, например `https://google.com/`; для проекта PM передаёт фактическую ссылку, согласованную с командой проекта.

Для test и prod запрашиваются отдельные deeplinks: это разные WebView и у них разные partner name. Если PM не знает точную целевую страницу, её нужно запросить у команды проекта до обращения в техподдержку.

### 6. Обсудить дополнительные возможности

- **Оплата:** если оплата входит в сценарий, в начале проекта договориться о встрече с ДЦРМС. Во время обсуждения определят вариант интеграции, например OTP-код или native payment.
- **Push:** детали payload и отправки находятся в документации backend-команды в Confluence. PM-база отсылает к backend-разработчику за актуальной документацией и не копирует её содержание.

### 7. Вывести сервис в production

Процесс в целом такой же, как для тестовой среды; остальные данные по сервису, домену и Bridge нужно продублировать. Телефоны сотрудников указываются только для тестовой среды. Если в production повторяется список сотрудников, передать ФИО и должности без номеров телефонов. PM указывает категорию сервиса внутри приложения; её выбирает владелец по назначению сервиса и логике приложения. Например, сервис может относиться к категории «Страхование». Для Bridge production origin запрашивается отдельно от других окружений.

## Письмо для настройки WebView

Заполнить поля по шаблону в [templates/webview-setup-email.md](./templates/webview-setup-email.md). Origin и capabilities PM получает у frontend. Нужность и значение callback/result URL уточняет у команды соответствующего flow. Для каждого окружения origins направляются отдельно.

## Роль PM-ассистента

PM-ассистент может:

- объяснить шаг процесса простыми словами и назвать следующую команду или канал по подтверждённой информации;
- составить Jira-заявку или письмо из сведений, которые предоставил PM;
- запросить у PM недостающие данные: серверные требования, домен/origin, capability, callback/result URL, целевую страницу deeplink, partner name, категорию сервиса;
- объяснить разницу между origin, capability и deeplink со ссылками на техническую документацию.

PM-ассистент не должен придумывать значения capabilities, домены, partner name, URL, категории, сроки и непредоставленные реквизиты Jira. Не отправлять заявки и сообщения от имени PM без отдельного поручения.
